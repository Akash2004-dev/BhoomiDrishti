# BhoomiDrishti

**Satellite-to-ground crop damage evidence for human review**

BhoomiDrishti is a prototype workflow that accepts field coordinates, an event date, farmer-provided notes, and a crop image. It requests a schema-constrained visual description from Gemini, queries Sentinel-2 surface reflectance through Google Earth Engine when access and suitable observations are available, runs deterministic prototype checks, and returns a dossier with a SHA-256 record fingerprint.

This is a decision-support prototype. It does not approve insurance claims or payouts, determine PMFBY eligibility, or implement an officially validated loss formula. The 60/40 visual/satellite weighting is an experimental prototype estimate. When satellite evidence is missing, the response labels it unavailable and does not substitute a made-up NDVI value. The 200 m region is a coordinate buffer, not a parcel/cadastral boundary.

## Pipeline

1. The browser submits a JPEG, PNG, or WebP image, WGS84 coordinates, event date, and optional text context.
2. FastAPI validates the request and passes the image to Gemini for structured visual observations.
3. The backend attempts a Sentinel-2 NDVI comparison with Earth Engine for the 30 days before and 15 days after the event date.
4. Deterministic code creates a prototype estimate only when live satellite evidence is returned; otherwise it marks the fused estimate unavailable.
5. The response includes provider provenance, human-review status, an advisory generated by the model, and a SHA-256 fingerprint of the returned record.
6. The UI displays the dossier. A hash can detect a change only when compared against a separately retained trusted copy; it does not itself prove who created the record or prevent edits.

Not implemented in the supplied prototype: weather API verification, Firestore persistence, real-time dashboard updates, cadastral parcel geometry, video upload, voice-note UI, or an official claims workflow.

## Requirements

- Python 3.11+
- Node.js 20 or later and npm
- A Gemini API key for live image analysis
- Optional Google Earth Engine service-account access, credential file, and Google Cloud project for satellite analysis
- Optional Google Maps browser key to render the map panel

## Local run (Windows PowerShell)

Backend terminal:

```powershell
cd backend
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
Copy-Item .env.example .env
# Set GEMINI_API_KEY in backend/.env. Configure Earth Engine separately if available.
python -m pip install -r requirements.txt
uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

Frontend terminal:

```powershell
cd frontend
Copy-Item .env.local.example .env.local
npm ci
npm run dev
```

Open <http://localhost:3000>. Backend health endpoint: <http://localhost:8000/health>. API documentation: <http://localhost:8000/docs>.

For live satellite results, configure `GOOGLE_APPLICATION_CREDENTIALS`, `GEE_SERVICE_ACCOUNT`, and `GEE_PROJECT_ID` in `backend/.env`; the service account must have Earth Engine access. Without these, the response explicitly says satellite evidence is unavailable. Do not commit `.env` files or credentials.

## Configuration

Copy `backend/.env.example` to `backend/.env`. Copy `frontend/.env.local.example` to `frontend/.env.local`. The backend defaults to the configured Gemini model `gemini-3.5-flash`; change `GEMINI_MODEL` only to a model enabled for your API project. Configure `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` only if the map panel is needed; restrict that browser key to the required APIs and allowed origins.

## Deployment

The backend Dockerfile supports Cloud Run, but no service, credentials, or live URL is included or verified. Configure secrets with the hosting platform's secret manager; do not place API keys in deployment command lines. The frontend has no Firebase Hosting configuration in this package, so Firebase deployment is not ready. Verify the app and provider access locally before deployment.
